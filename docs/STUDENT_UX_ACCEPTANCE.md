# 学生使用体验验收标准（持续迭代）

> 目标：学生只要提出一个自然语言问题，AI 就能正确定位资料；学生不必了解 GitHub 文件夹、目录格式和 PR。初版不承诺所有普通网页模型都能直接联网读取仓库。

## 路由验收用例

| 学生自然语言提问 | AI 应该读取 | 应该给出的反馈 |
|---|---|---|
| “2023年的数据结构期末卷从第一题开始讲” | HUB_INDEX → catalog.json | 先查是否有授权的原卷。当前未收录，明确承认缺失，可推荐真实存在的原创练习。 |
| “东林宿舍怎么样，有什么槽点？” | HUB_INDEX → discussion_catalog.json → 宿舍专题 | 按主题说明有公开资料讨论住宿，列出来源和年份；不能据此断定每个宿舍的条件。 |
| “校园网大家感觉怎么样？” | HUB_INDEX → discussion_catalog.json → 网络专题 | 说明不同来源各自的适用条件、历史年份，不推断全校网络质量。 |
| “最新转专业规则和学生吐槽是什么？” | HUB_INDEX → community_catalog.json + discussion_catalog.json/公开来源 | 正式规则必须核对当年官网。现有讨论未覆盖的内容要如实说缺失，不能编造当前规定或流行观点。 |
| “今天贴吧有人讨论什么？” | HUB_INDEX → 来源快照/如有实时读取工具再搜索 | 历史扫描不能当最新帖，若当日读取失败应说明“未能核实”。 |
| “把刚才我的经历加入仓库” | CONTRIBUTING 与 COMMUNITY_CONTRIBUTING | 只整理经过本人明确同意可公开的脱敏短稿；能写入时建立审核提案，不能自动泄露聊天全文。 |
| “用网页版DeepSeek直接打开仓库” | docs/CONNECTORS.md | 客户端未配 GitHub 工具时解释限制，不声称已读取，提供可接 GitHub/MCP 的客户端路线。 |

## 维护性能目标（非实际测量指标）

- **学生输入**：一句话，免学 GitHub；向 AI 查询时应当无需提交 Issue 才能获得答案。
- **AI 检索**：先读一个 `HUB_INDEX.json`，再读问题相关的1—2个模块索引和相应专题；避免每轮遍历全部仓库。
- **输出**：直接回答问题、给原始来源和时间、说明不确定/争议；不要把技术检索过程当成答案主体。
- **讨论主题**：优先复用已有专题，跨平台来源合并；无新信息时不制造重复卡。
- **投稿**：AI 能整理、去重、跑测试，但真实身份、校规冲突、隐私、版权仍需可信任维护者审核。
- **维护成本**：Markdown + JSON + GitHub Actions 即可运行基础版本；不用付费向量数据库或强制部署聊天服务器。

## 后续必须真实测试的三个瓶颈

1. **接入兼容**：不同 AI 产品是否真的能读取 GitHub，而不仅仅是复制 URL。
2. **内容覆盖**：只有3个讨论主题，不能代表东林学生各类需求；不可伪造覆盖率。
3. **更新时效**：第三方平台读取受限且没有定时 Agent；旧快照不能回答“今天发生了什么”。

只有拿到实际学生使用反馈后，才能评价平均响应步骤、检索准确率及满意度。自动校验通过只是保证文件结构，没有证实这些体验指标。
